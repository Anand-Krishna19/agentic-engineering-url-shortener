# ADR-003: Persistence Strategy: PostgreSQL, One Database per Plane

## Status

**Proposed (revised 2026-10-16, awaiting re-approval).** PostgreSQL was explicitly approved (DEC-060). The first version proposed two roles per plane (migration plus application); the human **rejected** that as unnecessary complexity that departs from the approved architecture (DEC-095). This revision uses a single application role per plane.

## Context

Both planes need durable, consistent state: mappings, idempotency records, counters, workflow state, approvals, and an append-only audit chain. The specification requires atomic behavior (FR-018, DEC-034), unique codes (FR-006), durable storage before success is reported (FR-019), append-only audit data (FR-130), and recoverable workflow state (FR-107). Data ownership must be separate per plane (plan section 1.5).

## Decision Drivers

ACID transactions, conditional updates and row locks (DEC-034, LIM-002), enforcement of append-only audit data, least privilege, deterministic time in tests (ADR-010), local runnability (K1, K9), reversibility.

## Options Considered

**A. PostgreSQL (approved).** Approach: two databases (`shortener`, `orchestrator`), SQL through `pg` behind repository ports, no ORM, numbered SQL migrations. Advantages: real transactions and locking; privileges and triggers enforce append-only audit tables; `timestamptz`, `jsonb`, and `COLLATE "C"` fit the data. Disadvantages: needs a running server (Docker is not running on this machine; neither PostgreSQL nor Redis is installed natively). Risks: R-23 prerequisites, R-24 test isolation cost. Impact: Compose file, per-worker test databases. Assessment: strongest consistency story.

**B. SQLite.** The planner's earlier proposal (superseded). Advantages: no server. Disadvantages: weaker concurrency and no privilege model. Risk: audit enforcement relies on triggers only. Assessment: simpler, but the human chose otherwise.

**C. Flat files plus JSON.** Advantages: trivial. Disadvantages: no atomicity or constraints. Rejected.

## Decision

Use **PostgreSQL** with **two databases** (`shortener`, `orchestrator`). Planner design inside the approved choice (confirmed as sub-selections, DEC-070):
- Driver `pg`; hand-written parameterized SQL behind repository interfaces; **no ORM**; numbered SQL migrations applied with `node-pg-migrate`.
- `timestamptz` timestamps; `jsonb` for structured payloads; short codes stored as `text` with the `"C"` collation so uniqueness is case-sensitive (ASM-015).
- Lease, expiry, retention, and rate-limit comparisons use a timestamp **passed in from the `Clock` port** (never `now()`).
- Default isolation `READ COMMITTED` with explicit conditional updates and row locks; the atomic check-and-commit is one transaction (ADR-026).
- Audit tables are append-only by **triggers and by revoked `UPDATE` and `DELETE` privileges** (ADR-006).
- **Roles (DEC-095):** **one application role per plane** (`shortener_app`, `orchestrator_app`): DML only, no DDL, and no `UPDATE` or `DELETE` on audit tables. There is **no persistent migration role**. Migrations run only through the explicit `migrate` command, which uses the container's administrative credential (generated by `orch init` into `.secrets/`) for the duration of that command; running services never read or hold that credential. This matches the approved plan text (one role per plane).

## Rationale

It gives the transactional semantics the specification depends on (DEC-034, FR-018) and lets the database itself enforce audit immutability, which is stronger than application-level controls. The human selected it for strong consistency and ACID.

## Consequences

- Positive: atomic commit and conditional updates are native; privileges back the audit claim.
- Negative: an external service is now a prerequisite; setup and test isolation take effort.
- Operational: Compose file for local PostgreSQL; secrets generated by `orch init`; migrations are an explicit step.
- Testing: real PostgreSQL in tests, one database per Vitest worker created from a template; migration up and down tests; privilege and trigger tests.
- Governance: schema changes follow the change-record process and G-CHG; destructive migrations need G-DESTR.

## Risks and Mitigations

- R-23 Docker and services unavailable: accepted (DEC-069); CP-1 requires them running; stop with NOT_READY and a blocker list if not.
- R-24 slow or flaky tests: template databases, key prefixes, fewer deeper integration tests.
- R-04 lock contention in concurrency tests: short transactions; repeated runs.
- Administrative credential handling: used only by the `migrate` command, never loaded by the shortener or orchestrator processes; covered by a test that the running services cannot perform DDL or modify audit rows.

## Reversibility

High for the data layer behind repository ports (a dialect adapter would be needed). Low for the specific atomic-commit design, which assumes a transactional store.
