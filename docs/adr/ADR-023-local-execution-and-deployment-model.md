# ADR-023: Deployment and Local Execution Model

## Status

**Accepted.** Approved by the human candidate on 2026-10-16, recorded as DEC-091. Clarifications: PostgreSQL 16 and Redis 7.2 pinned images, no CI platform, evidence organized by scenario. Amended by DEC-111 to DEC-113 (final report location, evidence retention, Compose and database settings).

## Context

The prototype is production-oriented but not production-scale and must be locally runnable by assessors. The approved stack needs PostgreSQL and Redis; on the candidate's machine Docker's daemon was not running and neither service is installed natively. Production deployment, a deployment platform, and TLS are out of scope (EXC-002), but the plan must say how the system runs.

## Decision Drivers

Local runnability; reproducibility; least infrastructure; safe defaults (loopback); clear stop conditions; honesty about prerequisites.

## Options Considered

**A. Dependencies in containers from one Compose file (PostgreSQL, Redis); the two Node processes and the CLI run on the host with npm scripts; everything bound to loopback.**
- Advantages: reproducible dependencies; fast application iteration; no native installs.
- Disadvantages: Docker must be running (a known prerequisite).
- Risks: R-23 Docker unavailable.
- Impact: Compose file, init and migrate scripts.
- Assessment: easiest for reviewers to run.

**B. Everything in containers, including the applications.** Advantages: uniform. Disadvantages: slower iteration; more images; closer to a deployment platform decision that is out of scope. Rejected.

**C. Native PostgreSQL and Redis installs.** Disadvantages: manual setup on Windows; irreproducible. Rejected.

**D. Cloud-hosted services.** Out of scope (EXC-002). Rejected.

## Decision

Use **option A**. Pinned container images in the **PostgreSQL 16 and Redis 7.2 lines** (DEC-098; the human's examples were `postgres:16.2-alpine` and `redis:7.2-alpine`; exact tags and digests are fixed and recorded at CP-1, PostgreSQL uses the **latest 16.x patch** because 16.2 predates later security fixes (human confirmation, DEC-098), and Redis stays on the 7.2 line; the 7.2 line is the last BSD-licensed Redis line, which suits POL-LIC-001), loopback-only ports, credentials generated by `orch init` into `.secrets/` (never committed); migrations are an explicit `migrate` step that uses the container's administrative credential only for that command (ADR-003, DEC-095); **there is no CI platform** and all verification is local through `npm run verify` (DEC-099); evidence is written under `evidence/`, organized by scenario (`evidence/scenario-a/`, `evidence/scenario-b/`, `evidence/scenario-c/`, plus `evidence/verify/` and `evidence/traces/`, DEC-100); the verify script runs everything and writes evidence; `quickstart.md` states the Docker prerequisite first. **Starting Docker Desktop and verifying PostgreSQL and Redis is a mandatory precondition (CP-1, DEC-069); if it cannot be done the project stops with NOT_READY and a documented blocker list.** Containers are a local-development convenience, not a deployment platform.

**Further decisions (DEC-111 to DEC-113).** The final report is the Markdown file `evidence/final-report.md` (summary of what was built, decisions made, test results, known limitations, and links to all evidence bundles); it is assembled from the per-run final summaries (FR-129), the verify output, and the trace report, and every claim links to recorded evidence. Evidence has no size limit, is retained for the duration of the assessment, and is committed to the GitHub repository so the reviewer can access it after submission, which means the secret scan covers `evidence/` and nothing from `.secrets/` or a database dump may be committed. The file is `docker-compose.yml`, with health checks for both services. **PostgreSQL:** `POSTGRES_USER=app`, `POSTGRES_DB=urlshortener`, no external connection pooler. **Redis:** the default image configuration with persistence turned off (ephemeral cache only). Interpretations applied so the human's settings do not break accepted ADRs (**all confirmed by the human on 2026-10-16**): (a) `app` is the container's **bootstrap/administrative** role, used only by `migrate`, because in the official image `POSTGRES_USER` is a superuser and a superuser service role would bypass privileges and triggers and defeat ADR-003 and ADR-006; services use `shortener_app` and `orchestrator_app`; (b) `urlshortener` is the application plane's database and the init script also creates the `orchestrator` database (ADR-003 keeps two databases); (c) "connection pooling disabled" means no external pooler such as PgBouncer, while the `pg` driver keeps a small fixed pool (confirmed: at most 10 connections per process) because a single connection would serialize requests and defeat the concurrency tests (FR-017, PVT-015); (d) "default configuration, no persistence" for Redis means the default image configuration plus `--save ""` and `--appendonly no`, and the password that ADR-015 requires, since the image default snapshots to disk and has no password.

## Rationale

It gives reproducible dependencies with minimal cost and keeps the application loop fast, while staying within the exclusion of production deployment.

## Consequences

- Positive: reviewers can run it; consistent environments.
- Negative: hard dependency on Docker.
- Operational: container health checks; data volumes are local and disposable; secrets handled as in security.md.
- Testing: tests use one database per worker and Redis key prefixes (PA-014); CP-1 round trip.
- Governance: no deployment is performed or claimed; the final report states the local-only scope.

## Risks and Mitigations

- R-23: CP-1 and SC-1 as above; the quickstart documents the first step.
- Port conflicts: ports checked free at init.
